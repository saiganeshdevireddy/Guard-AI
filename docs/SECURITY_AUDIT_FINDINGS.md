# Guard AI Browser Runtime Security Audit Findings

**Canonical security findings register.** Master decisions and component ownership are in [GUARD_AI_MASTER_ARCHITECTURE.md](GUARD_AI_MASTER_ARCHITECTURE.md); browser design is [ISOLATED_BROWSER_ARCHITECTURE.md](ISOLATED_BROWSER_ARCHITECTURE.md). [PRE_IMPLEMENTATION_SECURITY_AUDIT.md](PRE_IMPLEMENTATION_SECURITY_AUDIT.md) and [GUARD_AI_LOPWHole_AUDIT.md](GUARD_AI_LOPWHole_AUDIT.md) remain summaries/evidence; this file is the current finding register.

## Resolved architecture decisions (documentation only)

- Defence AI owns isolated browsing, URL protection, sandbox/private-session policy, isolation readiness and defensive session enforcement. Session Manager, Worker Supervisor, Egress Gateway, Display Gateway and Cleanup Manager execute under Defence policy. No such runtime capability is implemented.
- The target isolation unit is one disposable VM per browser session; tabs within a session share its profile/storage, while separate sessions do not. Ordinary incognito/private mode is not an isolation boundary. Session closure initiates cleanup; terminal destruction requires verification.
- Six target agents include Wi-Fi Analysis AI; source implementation still nests Wi-Fi under Finder.
- Canonical documents are `GUARD_AI_MASTER_ARCHITECTURE.md`, `ISOLATED_BROWSER_ARCHITECTURE.md`, and this register.

## Unresolved risks and decisions

Worker ownership/specification; hosting region and budget; privacy, consent, retention and deletion; local versus remote execution; concurrency/resource limits; display transport/authentication/topology/ports; egress DNS/proxy routes and allowed destinations; user/service authorization and identity issuance; Android scope; and named operational owners for operations, keys, audit, updates, privacy, recovery and incident response remain open. See the readiness checklist in [GUARD_AI_MASTER_ARCHITECTURE.md](GUARD_AI_MASTER_ARCHITECTURE.md) and [PRE_IMPLEMENTATION_SECURITY_AUDIT.md](PRE_IMPLEMENTATION_SECURITY_AUDIT.md). These decisions block implementation readiness.

## Fallback and validation crosswalk

The finding rows below provide source/effect, mitigation, verification criteria and implementation status. The operational fallback for each risk is explicit here; all are **required future behavior**, not implemented controls.

| Finding | Required fallback if mitigation/control fails | Validation gate |
|---|---|---|
| SA-01 URL/privacy retention | Stop forwarding raw session URLs; deny optional collection until redaction/retention policy is approved; restrict access and delete under approved policy. | Synthetic sensitive URL through every entry path; inspect DB, events, logs, API and Informer outputs. |
| SA-02 Misleading readiness | Never use heuristic `sandbox_ready`; deny launch unless separate authenticated worker/session readiness passes. | Fake/missing headers and stale/false readiness must never permit create. |
| SA-03 Worker authz | Revoke worker identity and deny new commands; isolate broker if scope is uncertain. | Wrong/revoked identity, operation, owner, image, replay and quota tests. |
| SA-04 Session capability | Revoke tickets and terminate affected stream/session; no reusable URL token or alternate handshake fallback. | Wrong origin/audience, expiry, replay, parallel redemption, logout/stop tests; inspect logs/referrers. |
| SA-05 Egress enforcement | Persistent host default-deny; fence guest and stop session on gateway/policy uncertainty; never direct-connect. | Packet tests for private/metadata/IPv6/rebinding/redirect/alternate transport and gateway outage. |
| SA-06 Display/input | Revoke display capability and stop session if route, origin, protocol or input validation fails. | ACL and cross-session tests; malformed frames, channel negotiation, flood and revocation tests. |
| SA-07 Cleanup | Mark `cleanup_pending`, quarantine worker capacity, revoke access/key and retry boundedly; operator response before reuse. | Inject partial failure and verify VM/process, route, ticket, key/profile status; do not claim physical erase. |
| SA-08 Remote API exposure | Keep control plane loopback/private; disable remote access until identity edge and controls are approved. | External unauthenticated access, origin, account abuse, rate, revocation tests. |
| SA-09 Untrusted content to agents | Drop/quarantine content-derived event; revoke implicated operation; preserve only allowlisted lifecycle metadata. | Prompt-injection and crafted title/error/frame tests cannot call agents, tools, APIs or worker. |
| SA-10 Readiness/restart | Deny creates, revoke streams, fence guest network and reconcile only tagged Guard AI sessions. | Stale health, restart, partition, firewall/gateway loss and unrelated-resource tests. |
| SA-11 Resource/control-plane abuse | Reject admission at hard caps; stop/fence abusive session; alert operator and retain safe mode if control identity compromised. | Saturation, quota bypass, budget alert, retry storm and compromised-identity tests. |
| SA-12 VM escape/supply chain | Isolate worker, revoke identities, preserve bounded evidence, quarantine host and restore only verified signed image after operator review. | Image provenance, host isolation, resource boundary, recovery and independent adversarial review. |

Validation must be executed on the selected infrastructure before claims of implementation or verification. A planned test is not a passed test.

**Scope:** source-backed review of the existing Guard AI code and proposed browser architecture before implementation. No runtime exists and this is not a penetration test. All future controls below are **proposed and unimplemented** unless a row explicitly describes current behavior.

| **SA-01 — High: raw URL retention** | URLs enter through `POST /api/v1/scan/url` (`URLScanRequest`) or can reach `FinderAI.scan_url()` via `POST /api/v1/agents/message` (`FinderAI.handle_message`) and `FINDER_SCAN_URL`; `SCAN_URL_REQUEST` also invokes the phishing agent directly. `scanner_api.py` rejects userinfo credentials and non-HTTP(S) schemes but returns the original URL; it does not redact query, fragment, path, or token-like values. Agent/event entry paths do not apply the route validator. `PhishingDetectionAgent.analyze_url()` parses query for heuristic keywords and includes the original URL in its result. `FinderAI.scan_url()` returns the raw target/details and emits `THREAT_REPORT_SUBMITTED` with raw indicator, details and URL-bearing description. `ControllerAI.process_threat_report()` persists indicator and serialized `details_json` in `ThreatEvent`; `/api/v1/scan/threats` returns those fields to `scanner:read` users. The event bus retains recent payloads, including URL-bearing agent events, and `/api/v1/agents/events` exposes them to `agents:read`. Controller also passes indicator/description to Informer. `HybridAIEngine.sanitize_pii()` only replaces email/IP/card-like patterns in an indicator used for a local explanation; it does not rewrite Finder reports, events, descriptions, or stored threat records and does not generally redact URL query tokens. By contrast, `/api/v1/sandbox/preview-url` performs local review and returns the URL but does not persist a threat record. No cloud provider is currently configured, so this is a local retention issue, not evidence of current cloud transmission. | Query parameters, fragments, identifiers, search terms and tokens can be retained in threat DB/event/report data and exposed to authorized readers or diagnostics. Userinfo credentials are rejected at the scanner route, but that does not sanitize other URL components; the agent/event paths do not provide the same route-level validation. Current records are **not sanitized** by this finding. | Keep browser session URLs out of Finder/Controller threat-report workflows and their generic event bus. If a user separately requests Finder analysis, produce a separate privacy-reviewed redacted representation; do not reuse it as the session launch URL. Decide whether only normalized hostname or a keyed/pseudonymous indicator is needed; strip query and fragment and review path retention. Avoid raw URLs in descriptions, metrics, errors and audit. Define access and retention. | Seed synthetic URLs with query token, fragment, path identifier and userinfo through each route/event entry path. Confirm raw values are not present in persisted threat/audit/session records, agent event history, Informer message, logs or API response except an explicitly authorized/redacted launch path; verify a redacted indicator remains useful. | **Existing retention behavior confirmed; mitigations proposed, not implemented.** |
| **SA-02 — High: heuristic field can be mistaken for sandbox readiness** | `backend/app/agents/specialized/browser_agent.py::inspect_destination()` returns `sandbox_ready: false` when called with `mock_headers=None`, but true whenever it receives a headers dictionary. `handle_message()` supplies `{}` when a direct agent message contains no headers, so `POST /api/v1/agents/message` can return `sandbox_ready: true` without fetching headers. The result scores mock header posture only; it has no VM/worker checks. The normal `sandbox_engine.py` and `/api/v1/sandbox/preview-url` path call it without mock headers, perform local review only and return `preview_available: false`. `/api/health` reports isolated preview disabled. | A consumer may interpret a heuristic/header result or endpoint response as proof that a worker or isolation boundary is available. That could permit unsafe browsing in a future integration. | Treat `sandbox_ready` as legacy heuristic output and never use it for launch authorization/readiness. Expose distinct concepts: heuristic assessment, local review API health, authenticated worker liveness, worker security readiness, verified session isolation. Only worker attestation/readiness plus explicit policy checks may permit a session. | Test direct-agent message with no headers, supplied fake headers, and normal URL review; none may enable launch. Negative worker readiness tests block create. API/docs/UI distinguish review availability from genuine isolated browsing. | **Current field behavior confirmed; isolation is absent; correction proposed, not implemented.** |
| **SA-03 — High: worker authentication is not authorization** | No worker broker or worker credentials exist. The proposed architecture names private mTLS and typed calls but needs per-operation and per-session authorization. Existing user authentication is a FastAPI bearer JWT/role check in `backend/app/security/auth.py`; it is not worker identity and should not be forwarded. | A valid worker certificate could otherwise authorize overly broad VM operations; forged owner/session fields or a compromised FastAPI process could create/destroy arbitrary workloads or exceed resource limits. | Separate worker service identity from user principal. Enforce broker allowlist by caller, operation, owner, session ID, fixed image/policy, resource envelope and global/per-user quotas. Integrity-protect owner context; define certificate issuance, expiry, rotation, revocation, emergency disable, timestamp/nonce, idempotency and replay handling. Never pass user JWTs into guests. | Negative tests for wrong peer, revoked/expired identity, unauthorized operation/session/owner, arbitrary image/config/command, replay, duplicate create and quota exceedance; authorized scoped calls succeed. | **No worker auth exists; requirements are proposed, not implemented.** |
| **SA-04 — High: session capability protocol incomplete** | No browser session or display-ticket endpoint exists. Plans call for short-lived single-use tickets but do not yet define a complete browser-compatible issuance/redemption protocol. | Ticket theft, concurrent replay, wrong-user/session access, leakage through URL/access logs/referrer/analytics, or lingering access after logout/stop can expose the remote browser session. | Issue a high-entropy opaque capability through an authenticated API; store only its hash; bind to user, session, audience, origin and expiry; redeem atomically once; revoke on stop/logout/expiry; define clock skew/key rotation and shared gateway replay state. Avoid URL secrets. Choose and review a browser-compatible same-origin HTTPS/WebSocket handshake, including cookie and CSRF/origin implications. | Wrong binding, wrong origin, expiry, revocation, logout, stop, replay and concurrent redemption all fail; authorized client succeeds; secret absent from URLs, referrers, application/proxy logs and analytics. | **No session capability exists; controls proposed, not implemented.** |
| **SA-05 — High: network policy must be enforced outside Firecracker** | No guest network exists. Firecracker attaches guest networking through host interfaces; VMM documentation states host networking/firewall configuration is operator responsibility. The current docs describe gateway rules but leave route/interface/port details and deployed enforcement absent. | Guest or browser compromise could reach loopback, host services, LAN, peer sessions, control plane, cloud metadata, or bypass proxy policy; DNS rebinding and redirect handling can expose private destinations. | Use default-deny TAP/host forwarding; guest only reaches explicitly allowed proxy and per-session display endpoint. Validate connection-time DNS/IP, pin approved destination, revalidate redirects/retries, reject IPv4/IPv6 private/loopback/link-local/reserved/multicast/metadata and mapped/NAT64 cases. Disable direct DNS, DoH policy bypass, UDP/QUIC/WebRTC and unapproved ports. Keep egress gateway off management routes. | Packet-level tests from guest and compromised-guest simulation prove no host/LAN/control/metadata/private/canary reachability; tests cover IPv4/IPv6 literals, rebinding, redirects, proxy outage, direct DNS/UDP and every route. | **No worker network policy exists; requirements proposed, not implemented.** |
| **SA-06 — High: display topology and input boundary unresolved** | Guacamole/VNC remains proposed and unselected. The canonical design separates display from egress, but exact interface, endpoint, port, direction and ACL are still pending transport selection. No remote display/input code exists. | An overly broad display route can bridge sessions or management networks. Malformed display frames or input channels can attack the gateway/client or enable clipboard/file/device transfer. | Select transport and specify per-session topology, network, endpoint, ports, ACL and direction. Limit input to validated, rate/size-bounded keyboard and pointer messages; disable clipboard, file transfer, drive/device redirection and protocol extensions. Treat both display decoder and guest VNC endpoint as untrusted attack surfaces. | Network tests show only the authorized gateway can access only its assigned display endpoint. Fuzz/negative tests cover malformed frames, channel negotiation, oversized/rate-flooded input, cross-session routing, clipboard/file transfer and stream revocation. | **Display/input service absent; topology and controls proposed, not implemented.** |
| **SA-07 — High: cleanup request is not proof of destruction** | No session, VM, profile, disk or cleanup logic exists. Plans previously described overlay deletion as verification. Deleting a file does not establish physical erasure on SSDs or remove copies in swap, crash dumps, snapshots/backups. | Sensitive page state or credentials may remain recoverable; a stale VM/display mapping/key may remain usable after the user sees “stopped.” | Use unique encrypted per-session writable storage and destroy its data key; invalidate credentials/tickets; terminate the VM process/cgroup; detach/restrict network; remove profile/overlay access; suppress snapshots/backups and review swap/crash dumps. Record each verification result. Mark `cleanup_pending` and quarantine uncertain resources; never report `destroyed` on a cleanup request alone. | Independently confirm process/VM absence, network ACL detach, key destruction, credential and ticket revocation, profile no longer decryptable, and restart reconciliation. Inject partial cleanup failures and verify quarantine/alert/retry; never claim physical media sanitization from unlink. | **No cleanup exists; verifiable checklist proposed, not implemented.** |
| **SA-08 — High: API is not ready for remote exposure** | `backend/app/main.py` binds to loopback; frontend API client uses bearer authorization in JavaScript memory. Existing architecture docs identify same-origin script compromise and absent production controls; no remote identity gateway/session UI is deployed. | Direct LAN/public exposure could enable token theft, unauthorized session creation, CSRF/origin mistakes in a future cookie-based stream handshake, account abuse or worker control-plane exposure. | Keep development loopback. Before remote clients, approve an HTTPS identity edge, explicit origins, account protection, rate limits, logging/privacy, user consent and incident ownership. Keep worker/broker/supervisor private. Design WebSocket auth independently from the existing bearer API. | External unauthenticated requests cannot reach privileged API/worker operations; origin and auth tests cover browser and mobile clients; rate-limit/abuse tests and token revocation pass. | **Loopback prototype behavior exists; remote security design is incomplete and unimplemented.** |
| **SA-09 — High: untrusted content must not reach agent instructions** | No browser content is currently fetched. Finder/Controller event bus accepts payload dictionaries and retains recent payloads; URL scan event data is user-controlled. The proposed remote display avoids page DOM in React but display frames, titles/errors and user input remain untrusted. | A future integration could turn page text or crafted metadata into instructions/actions for trusted agents, leak content to Informer, or trigger unauthorized lifecycle operations. | Pass only allowlisted lifecycle events and opaque session IDs to agents. Keep session launch URL and page content outside generic threat events. Never feed DOM, scripts, screenshots, page text, or protocol frames to agent prompts/tools. FastAPI remains the user authorization boundary; Controller coordinates only authorized requests. | Inject page-like instructions, script/title/error payloads and malformed event fields; prove they cannot invoke agents, worker operations, external reporting, or change policy. Confirm Finder scores cannot auto-launch or certify safety. | **No browser-to-agent path exists; boundary proposed, not implemented.** |
| **SA-10 — High: liveness/readiness and failure fencing unspecified** | No worker health service, readiness attestation, watchdog or restart reconciliation exists. A running process alone would not establish KVM, image, firewall, gateway, display or cleanup health. | A stale/partial worker or gateway failure may still accept sessions or leave guests with direct egress after network policy disappears. | Separate liveness from readiness and require fresh authenticated checks for KVM, image digest/signature, jailer/config, resource headroom, actual routes/firewall rules, gateway/display, clock, disk and cleanup backlog. On loss, local host firewall remains default deny; revoke streams, fence guest network, stop/reconcile owned VMs and block creates. | Fault injection for worker restart, network partition, stale health, firewall removal, gateway/display outage and state-store loss proves no new session or egress bypass; stale owned sessions are reconciled and unrelated resources remain untouched. | **Health/watchdog absent; controls proposed, not implemented.** |
| **SA-11 — High: resource and control-plane abuse** | No admission control or VM resource limits exist. Proposed resource numbers are estimates; the current event bus is synchronous and in-process. | Session floods, hostile pages, stream encoding or cleanup storms can exhaust CPU/RAM/disk/network or incur unbounded cost; a compromised API identity may consume its authority. | Set approved hard per-session and global CPU/RAM/disk/time/byte/connection limits, per-user quotas and admission control enforced again on worker. Add spend alerts, bounded retries, cleanup backlog circuit breaker and operator stop switch. | Load tests demonstrate hard caps and deterministic rejection at configured ceilings; over-limit sessions are fenced/stopped; cleanup retry does not amplify overload; spend alerts are exercised. | **No runtime caps/quotas exist; proposal and values pending, not implemented.** |
| **SA-12 — High: browser/VM escape remains possible** | There is no runtime. Proposed microVM isolation relies on host Linux/kernel, KVM, Firecracker/jailer, guest kernel/browser, image builder and privileged networking. | Browser or VM escape could compromise worker, other sessions or control-plane data; no VM boundary guarantees immunity from zero-days. | Use patched pinned images, jailer/default seccomp, unique per-VM identities, cgroups/namespaces, no host mounts/secrets/devices, least privilege, independent review and adversarial tests. Keep management and control networks separate; do not make production multi-tenant claims without evidence. | Verify image provenance, resource/privilege boundaries, session noninterference, crash/escape test plan, host patch process, and no management reachability; independent reviewers sign off residual risks. | **No runtime boundary exists; all mitigations proposed, not implemented.** |
